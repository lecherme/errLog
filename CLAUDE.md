# Project instructions

## Git changes: mandatory safe-commit workflow

Use `node tools/safe-commit.mjs` as the only way to stage, commit, or push work in
this repository. Apply this protocol at the end of every completed and tested stage.

### Prepare and review

1. Run the tests appropriate to the stage.
2. Inspect the worktree and identify the exact files owned by this stage. Never include
   unrelated user changes merely because they are present.
3. Write a request JSON under `.git/safe-commit/requests/` that conforms to
   `docs/safe-commit-request.schema.json` and contains only those exact paths.
4. Run exactly (replace the filename, without shell quoting or substitution):

   ```bash
   node tools/safe-commit.mjs check --request .git/safe-commit/requests/<request-name>.json --json
   ```

5. Show the user the plan ID, commit message, included files, ignored unrelated changes,
   and any errors. `check` may create private plan metadata, but it does not modify the
   index, create a commit, or push.
6. Stop and obtain explicit approval for that plan. Never invoke `commit` in the same
   command batch or automatically continue after `check`.

### Commit approval

Only after the user approves the displayed plan, run exactly (the plan ID is the
64-character hexadecimal ID returned by `check`):

```bash
node tools/safe-commit.mjs commit --plan <plan-id> --json
```

Do not add `--push`. Report the resulting commit SHA and remaining worktree changes.
If the plan is stale or fails, return to `check`; never bypass the failure with Git.

### Separate push approval

After a successful commit, ask separately whether to push that exact commit and name
the destination remote and branch. Only after explicit approval,  run:

```bash
node tools/safe-commit.mjs push --plan <plan-id> --json
```

If repository policy denies push, report `PUSH_DENIED`; do not fall back to direct
`git push` or weaken `.safe-commit.json` without separate user authorization.

### Forbidden bypasses

Never run direct Git mutation commands, including `git add`, `git commit`, `git push`,
`git merge`, `git cherry-pick`, `git revert`, `git reset`, `git restore --staged`,
`git commit-tree`, `git update-index`, or `git update-ref`, through alternate paths,
`git -C`, aliases, shell wrappers, substitutions, quoting tricks, or compound commands.
Never amend, force-push, or use broad staging such as `git add .` or unscoped
`git add -A`.

Only the simple read-only Git commands explicitly accepted by the gate remain allowed;
unknown subcommands and aliases fail closed. Do not edit this file, the project settings,
the gate, or `.safe-commit.json` merely to bypass a denied operation.

## Implementation stage workflow

OpenSpec (`openspec/changes/<change>/proposal.md|design.md|specs/*.md|tasks.md`) is
the single source of truth for product requirements, design, and implementation tasks.
The OpenSpec task checkbox is the only authoritative record of task completion.

- Work one small batch of related OpenSpec tasks at a time. Never have more than one
  open Stage Contract.
- Before editing any code, present a Stage Contract and obtain explicit approval.
  A Stage Contract states: stage ID; OpenSpec task IDs; expected outcome; the
  requirement/scenario/design it traces to; dependencies; sub-steps; the exact paths
  allowed to change; what is explicitly excluded; test requirements; contract-test
  requirements; AI-eval requirements; user-journey E2E requirements;
  security/privacy/trust-boundary impact; evidence
  of completion; and rollback approach.
- If implementation surfaces a spec gap, conflict, or a need to change requirements,
  stop coding and return to OpenSpec refine. Never change product semantics unilaterally.
- For deterministic logic and bug fixes, establish failing evidence first, then
  implement, then confirm the test passes.
- For UI, integration, and AI capabilities, use the fitting integration/E2E/eval
  approach — don't write low-value unit tests purely for form's sake.
- Any stage that adds or changes user-visible behavior must include persistent
  Playwright user-journey E2E derived from the OpenSpec Requirement/Scenario (design
  D22): driven only through the real UI, asserting business and user-visible outcomes,
  using synthetic data and deterministic test adapters for third-party providers,
  committed to the repo, and run by the same local gate and CI. `not-applicable`
  requires a stated reason. Temporary scripts, manual walkthroughs, DB injection, or
  internal API calls are never product E2E.
- User-visible stages use a bounded-context E2E worker after Stage Contract approval;
  the worker must return the mandatory structured E2E Test Summary, and a separate
  read-only reviewer must review the result. Large logs/traces remain in artifacts, not
  the main context. See `docs/implementation-workflow.md`.
- After implementation, run an independent read-only review. The reviewer reports only:
  blocking findings, non-blocking findings, evidence checked, and a verdict.
- At most two rounds of targeted fixes. If blocking findings remain after that, stop
  and report — don't loop indefinitely.
- A `tasks.md` checkbox may be checked only after implementation, local verification,
  and the independent review have all passed — remote CI is a separate, post-push
  re-verification and merge/release gate, not a precondition for this.
- Review small stages independently; run one convergence review after completing a
  Group or a key end-to-end flow.
- Every verified stage still goes through the full safe-commit protocol above:
  `check → user approval → commit → ask separately about push → user approval → push`.

Full procedure, Stage Contract template, and CI/contract-test/AI-eval/review details:
see `docs/implementation-workflow.md`.

## Session continuity and recovery

Any new Claude Code session must resume from disk alone — repository, worktree, and Git
state — never from chat history, `resume`, context, or model memory.

- Sources of truth: OpenSpec task checkboxes (completion), Git commits (durable stage
  boundaries), the current change's `scratchpad.md` Implementation Checkpoint (recovery
  notes for the single in-progress stage only), and the uncommitted worktree (possible
  in-progress work — never proof of completion by itself).
- At the start of every implementation session: read `CLAUDE.md` and
  `docs/implementation-workflow.md`, read the current change's planning artifacts and
  `scratchpad.md`, inspect branch/HEAD/upstream/worktree diff, cross-check the
  Implementation Checkpoint against actual files and Git state, and report findings
  before continuing.
- On any drift between checkpoint, worktree, Git, and task checkboxes: stop and report
  it. Never guess which source is correct, never delete or overwrite unexplained
  changes, never auto-check a task, never re-run an operation with external side effects.
- Once remote CI is configured, a new session must check the pushed HEAD's remote CI
  status before treating a stage as safe to build on; `failed`, `pending`/`running`, or
  `unknown` must never be treated as `passed`.

Full recovery protocol: see `docs/implementation-workflow.md`.

## Cross-agent review handoff

Optional, only when the user asks for a cross-agent (e.g. Codex) review. It sits after the
local gate and the Claude stage reviewer PASS, and before checking `tasks.md`, setting
`ready_for_safe_commit`, or running safe-commit `check`. Full protocol:
`docs/implementation-workflow.md` ("Cross-agent review handoff").

- Publish a review request only with `node tools/stage-handoff.mjs publish …`, then stop.
  Never invoke Codex or any other agent yourself, and never write a response yourself.
- Files under `.agent-handoffs/` (Git-ignored) are immutable: never edit, overwrite,
  rename, or delete them, or interrupted-write leftovers, unless the user explicitly asks.
  A targeted fix or a replaced safe-commit plan needs a new request revision.
- When the user says to read the current Codex response, run `verify` first. Use the
  response only if `verify` reports `valid`; otherwise report `handoff unavailable or
  invalid — perform direct repository review` and do not use it. Continue the workflow
  only on a Codex `PASS`; on `FAIL` or `BLOCKED`, stop and report.
- A handoff is a redacted review snapshot, not a source of truth. It never changes the
  checkpoint, tasks, or session recovery, never blocks a stage, and never authorizes a
  fix, commit, push, merge, or deployment. A fix for a Codex finding needs the user's
  instruction and shares the two-round targeted-fix limit with the Claude reviewer.
- Never put secrets, connection strings, environment dumps, real emails or phone
  numbers, photo/PDF content, or raw terminal output in a handoff; commands only in
  redacted form.
