# Project instructions

## Git changes: mandatory safe-commit workflow

Use `node tools/safe-commit.mjs` as the only way to stage, commit, or push work in
this repository. Apply this protocol at the end of every completed and tested stage.

### Prepare and review

1. Run the tests appropriate to the stage.
2. Inspect the worktree and identify the exact files owned by this stage. Never include
   unrelated user changes merely because they are present.
3. Write a request JSON under `.git/safe-commit/requests/` that conforms to
   `docs/safe-commit-request.schema.json` and contains only those exact paths.
4. Run exactly (replace the filename, without shell quoting or substitution):

   ```bash
   node tools/safe-commit.mjs check --request .git/safe-commit/requests/<request-name>.json --json
   ```

5. Show the user the plan ID, commit message, included files, ignored unrelated changes,
   and any errors. `check` may create private plan metadata, but it does not modify the
   index, create a commit, or push.
6. Stop and obtain explicit approval for that plan. Never invoke `commit` in the same
   command batch or automatically continue after `check`.

### Commit approval

Only after the user approves the displayed plan, run exactly (the plan ID is the
64-character hexadecimal ID returned by `check`):

```bash
node tools/safe-commit.mjs commit --plan <plan-id> --json
```

Do not add `--push`. Report the resulting commit SHA and remaining worktree changes.
If the plan is stale or fails, return to `check`; never bypass the failure with Git.

### Separate push approval

After a successful commit, ask separately whether to push that exact commit and name
the destination remote and branch. Only after explicit approval,  run:

```bash
node tools/safe-commit.mjs push --plan <plan-id> --json
```

If repository policy denies push, report `PUSH_DENIED`; do not fall back to direct
`git push` or weaken `.safe-commit.json` without separate user authorization.

### Forbidden bypasses

Never run direct Git mutation commands, including `git add`, `git commit`, `git push`,
`git merge`, `git cherry-pick`, `git revert`, `git reset`, `git restore --staged`,
`git commit-tree`, `git update-index`, or `git update-ref`, through alternate paths,
`git -C`, aliases, shell wrappers, substitutions, quoting tricks, or compound commands.
Never amend, force-push, or use broad staging such as `git add .` or unscoped
`git add -A`.

Only the simple read-only Git commands explicitly accepted by the gate remain allowed;
unknown subcommands and aliases fail closed. Do not edit this file, the project settings,
the gate, or `.safe-commit.json` merely to bypass a denied operation.
