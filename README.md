# errlog

## Safe commits

`tools/safe-commit.mjs` is a task-agnostic commit/push executor for any harness,
including future tools such as Superflowers. The harness supplies an exact file list
and commit message; the script checks policy, creates a reviewable plan, commits only
the approved Git content, and returns stable process and symbolic error codes. It has
no OpenSpec dependency. See [the safe-commit protocol](docs/safe-commit.md) for the
request schema and integration flow.

## OpenSpec setup

The standard Claude Code commands and skills under `.claude/` are generated locally
and are intentionally not committed. After cloning the repository, install the pinned
OpenSpec version and initialize the Claude integration:

```bash
# Requires Node.js 20.19 or newer.
npm install -g @fission-ai/openspec@1.10.0
openspec --version
openspec init --tools claude --profile core
```

The repository does track its project-specific OpenSpec content:

- `openspec/config.yaml`
- `openspec/specs/**`
- `openspec/changes/**`, including each change's `scratchpad.md`
- `.claude/commands/opsx/refine.md`
- `.claude/skills/openspec-refine-change/SKILL.md`

The two `refine` files are repository-owned customizations and are not generated by
OpenSpec 1.10.0. Review them explicitly before upgrading OpenSpec or switching workflow
profiles, because a future OpenSpec release may introduce a conflicting workflow.

## Local development stack

`compose.yaml` runs a local-development-only skeleton as the fixed Compose project
`errlog-dev`: `web` (Next.js, `apps/web/`), `pdf-processing` (a placeholder Python
service in `services/pdf-processing/`, replaced by the real PDF Processing Service in
task 3.1), and `db` (PostgreSQL). The three services reach each other by service name
on the project's own Compose bridge network. Run the commands below from the
repository root. Only `web` is published to the host, and only on host
loopback, by default at `http://127.0.0.1:3100`; `db` and `pdf-processing` publish no
host ports. If host port 3100 is already in use, set `ERRLOG_WEB_PORT` in the current
shell before starting (it still binds to `127.0.0.1` only).

`POSTGRES_PASSWORD` is required and must come from your shell environment. Never write
it into a committed file. Every `docker compose` command parses `compose.yaml`, so each
one needs the variable set in the same shell:

```bash
export POSTGRES_PASSWORD='<a local-only value>'
# export ERRLOG_WEB_PORT=3101          # optional, only on a host port conflict
docker compose up -d --build --wait   # start; open http://127.0.0.1:3100 (or your port)
docker compose down                   # normal stop
```

PostgreSQL data is stored in the project's named volume `errlog-dev_pgdata` (this name
assumes `COMPOSE_PROJECT_NAME` is not set, since it overrides the project name). It
persists across `docker compose down` and across rebuilding or recreating `web` and
`pdf-processing`. `docker compose down -v` or `docker volume rm` permanently delete this
local development database. Use them only when you deliberately want to discard that
data, never as the everyday stop command.
`POSTGRES_PASSWORD` only takes effect the first time the volume is initialized. Changing
it later does not change the database password.

CI, E2E runs, and temporary verification must never use the `errlog-dev` project name.
Pass a different project name (`docker compose -p <name> ...`) so they get their own
volume and never touch `errlog-dev_pgdata`.

Verify that the services reach each other by service name (after `up --wait`):

```bash
docker compose exec -T web node -e "fetch('http://pdf-processing:8000/',{signal:AbortSignal.timeout(4000)}).then(r=>process.exit(r.ok?0:1),()=>process.exit(1))"
docker compose exec -T web node -e "const s=require('net').connect(5432,'db');s.setTimeout(4000,()=>process.exit(1));s.on('connect',()=>process.exit(0)).on('error',()=>process.exit(1))"
docker compose exec -T pdf-processing python -c "import urllib.request; urllib.request.urlopen('http://web:3000/', timeout=4)"
docker compose exec -T pdf-processing python -c "import socket; socket.create_connection(('db', 5432), 4).close()"
docker compose exec -T db bash -c 'exec 3<>/dev/tcp/web/3000 && exec 4<>/dev/tcp/pdf-processing/8000'
```

### Database migrations

The schema lives in forward-only SQL migrations in `apps/web/db/migrations/`, applied by
node-pg-migrate. Migrations never run when `web` starts. Apply them explicitly with a
one-off `web` container, which uses the migration files built into the image (rebuild
after adding one) and reads the connection string from `DATABASE_URL`, passed by name
only. Build it from `POSTGRES_PASSWORD` rather than typing it, and never print it
(URL-encode the password if it contains reserved characters):

```bash
export DATABASE_URL="postgres://postgres:${POSTGRES_PASSWORD}@db:5432/postgres"
docker compose build web
docker compose run --rm --no-deps -e DATABASE_URL web npm run db:migrate
unset DATABASE_URL
```

A repeated run reports `No migrations to run!`. Never change a migration that is already
in Git history; add a new one instead.

`npm run test:db` checks the schema constraints. Run it only against a disposable,
already-migrated database in a separate Compose project (`-p <name>`), never against
`errlog-dev`. It reads only `ERRLOG_SCHEMA_TEST_DATABASE_URL` (passed by name, like
above) and rolls back everything it writes:

```bash
docker compose -p <name> run --rm --no-deps -e ERRLOG_SCHEMA_TEST_DATABASE_URL web npm run test:db
```
